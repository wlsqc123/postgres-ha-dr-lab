# 면접 설명 요약

## 30초 소개

PostgreSQL 두 대로 물리 복제를 구성하고, 이체 부하 중 Primary를 강제 종료해 수동 장애 전환을 검증했습니다. 서버 승격뿐 아니라 승인 거래의 유실과 재시도 중복 여부를 따로 확인했습니다. 기존 Primary 재편입, 동기·비동기 복제 비교, 삭제 직전 시점으로의 PITR도 실험했습니다.

## 핵심 질문

| 질문 | 답변 핵심 |
|---|---|
| 어떻게 장애를 만들었나요? | `docker compose kill -s SIGKILL primary`로 DB 프로세스를 종료했습니다. 종료 코드 137과 실제 클라이언트 실패를 확인했습니다. |
| 어떻게 승격했나요? | 구 Primary 정지·restart=no·차단 표식을 확인한 뒤 `pg_promote(false)`를 호출했습니다. recovery=false와 Timeline 증가를 별도로 확인했습니다. |
| 13.828초가 승격 시간인가요? | 장애 요청부터 앱의 첫 쓰기 성공을 관측할 때까지입니다. 차단과 검증도 포함합니다. 승격 요청부터 완료 확인은 1.782초였습니다. |
| 유실은 어떻게 찾았나요? | 재시도 전에 클라이언트 승인 ID와 새 Primary를 비교했습니다. 먼저 재시도하면 유실 거래가 재생성돼 최초 유실을 가릴 수 있습니다. |
| 중복 반영은 어떻게 막았나요? | 요청 ID 유일성 제약과 payload 비교를 사용했습니다. 이력·출금·입금·원장을 하나의 트랜잭션으로 커밋하고 독립적인 기대값과 대조했습니다. |
| 동기 복제에서 무엇이 달랐나요? | Standby 중단 중 비동기는 승인을 계속했고 동기는 SyncRep에서 기다렸습니다. 복제 단절 후 Primary를 종료한 실험에서 승인 유실은 각각 10/321건과 0/311건이었습니다. |
| 왜 pg_rewind 대신 새 백업을 썼나요? | 작은 실습 데이터에서 장애 디스크를 보존하고 새 Primary의 전체 복사본으로 재구성하는 절차를 먼저 검증했습니다. 큰 데이터에서는 복사량과 시간이 부담이 됩니다. |
| 단순 백업 복원과 PITR을 어떻게 구분했나요? | 백업에는 요청 1건만 넣고 이후 정상 거래 2건을 추가했습니다. 복구 결과가 3건이며 목표 이후 거래와 삭제가 제외되는지 확인했습니다. |
| WAL이 빠지면 어떻게 됐나요? | 필수 WAL 하나를 restore_command에서 제공하지 않자 목표 미도달 오류와 종료 코드 1로 실패했습니다. 실제 보관 파일은 삭제하지 않았습니다. |

## 혼동하지 않을 숫자

| 실험 | 결과 | 의미 |
|---|---|---|
| 정상 복제 중 첫 장애 전환 | 승인 유실 0/159건 | 비동기 무손실 보장은 아님 |
| Standby 중단 후 장애 비교 | 비동기 10/321건, 동기 0/311건 유실 | 의도적으로 복제를 끊은 별도 실험 |
| 정상 이체 각 300건의 p95 | 비동기 21.545ms, 동기 28.664ms | 연결 수립을 제외한 이체 승인 지연 |
| 재편입 후 | 요청 206건·원장 412건 | 재편입 전후 검증에 새 거래 1건 포함 |
| PITR 목표 시점 | 요청 3건·원장 6건 | 복구 후 쓰기 확인을 더하면 4건·8건 |

## 직접 검증하지 않은 범위

자동 장애 전환, 네트워크 분할, pg_rewind, 원래 서버로 역할을 되돌리는 failback, 호스트 전체 유실은 검증하지 않았습니다. 파일 기반 차단과 라우팅을 운영용 STONITH·프록시 구성으로 설명하지 않습니다. 동기 실험의 미승인 요청 1건도 롤백으로 단정하지 않고 결과 불명확으로 기록했습니다.
